# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Proyecto

**Bingo**: app web de gastos mensuales (idioma de la UI: español), con la marca basada en Bingo, el perro salchicha rojo del dueño. Core: registrar ingresos y gastos, y generar resúmenes/análisis mensuales (cuánto ingresó, cuánto se gastó y en qué). Las categorías y subcategorías (ej. "Carro" > "Seguro") las define el propio usuario, no son fijas. Login con Google; los datos se guardan por usuario.

Stack: Next.js (App Router, `src/` dir, alias `@/*`), TypeScript, Tailwind CSS v4, shadcn/ui (estilo radix-nova, íconos lucide), zod, Firebase (Auth con Google + Firestore vía firebase-admin). Diseño mobile first.

Moneda, locale y zona horaria se configuran en `src/lib/config.ts` (por defecto ARS / es-AR / Buenos Aires).

## Comandos

```bash
npm run dev      # servidor de desarrollo (Turbopack)
npm run build    # build de producción
npm run lint     # ESLint
```

No hay framework de tests configurado todavía. Componentes shadcn nuevos: `npx shadcn@latest add <nombre>` (quedan en `src/components/ui`, no editarlos salvo necesidad).

## Configuración de Firebase

Copiar `.env.example` a `.env.local` y completar las variables `NEXT_PUBLIC_FIREBASE_*` (Firebase Console > Project settings > Web app). `.gitignore` ignora `.env*` salvo `.env.example`. Hay que habilitar el proveedor Google en Firebase Authentication.

## Arquitectura

### Autenticación (Google + cookie de sesión)
Flujo: el cliente hace `signInWithPopup` (`components/auth/GoogleSignInButton.tsx`) → manda el ID token a la Server Action `createSession` (`lib/auth/actions.ts`) → el servidor lo verifica con firebase-admin y guarda una cookie httpOnly `session` (5 días). La sesión vive en la cookie, no en el SDK cliente (el SDK cliente cierra su sesión tras crear la cookie; el popup se abre sin `await` previos para que mobile no lo bloquee).

- `lib/firebase/client.ts`: SDK cliente, solo `auth` (Firestore se usa únicamente desde el servidor). Solo para componentes `"use client"`.
- `lib/firebase/admin.ts`: SDK admin, `server-only`, init perezoso vía `getAdminAuth()` (el build no requiere credenciales; el runtime sí: `FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY`).
- `lib/auth/session.ts`: DAL. `getSessionUser()` (devuelve null) y `verifySession()` (redirige a `/login`). Usar `verifySession()` en cada página/acción protegida y, más adelante, antes de leer/escribir datos del usuario.
- `proxy.ts` (reemplaza a `middleware` en Next 16): solo chequeo optimista de presencia de cookie para redirigir a `/login`. `/login` queda excluido a propósito (evita bucle con cookie inválida); esa página redirige a `/` si la sesión es válida.

### Rutas y renderizado
`next.config.ts` tiene `cacheComponents` y `partialPrefetching`: acceder a `cookies()`/datos de runtime fuera de `<Suspense>` rompe el build. Patrón usado: shell estático + componente async con la sesión envuelto en `<Suspense>` (ver `components/layout/Header.tsx`, `(app)/page.tsx`).
- `src/app/(auth)/login`: pública.
- `src/app/(app)/`: rutas protegidas. `/` es el resumen del mes (`?m=YYYY-MM` para meses pasados; hacia atrás hasta el primer mes con movimientos; hacia adelante del mes actual solo a meses que tengan movimientos propios, vía `getFutureMonths`). Arriba, `BalanceViewSwitcher` cambia entre Mes, Período (`?v=periodo&d=&h=`) y General (`?v=general`, desde el primer movimiento hasta hoy; lógica en `lib/finance/balance-view.ts`); la última elegida queda en la cookie `balanceView` y un `?m=` siempre fuerza la vista mensual. Bingo y los presupuestos siguen mirando el mes. `/negocio` es Mi negocio (`BusinessView`; `/emprendimiento` redirige ahí desde `next.config.ts`). `/categorias` es el panel de categorías. `/tarjetas` es el panel de tarjetas y cuotas (cada tarjeta muestra el próximo vencimiento y pliega con un chevron los próximos resúmenes y las cuotas); `/tarjetas/[id]?m=YYYY-MM` es el detalle de consumos de un resumen, con navegación entre meses, marcar como pagado y edición de cada consumo (alias, descripción, categoría, monto desde esta cuota o en todas, eliminar). `/ahorros` es la página de metas (`GoalsView`). `/contactos` es la página de contactos (`ContactsView`). `/compartidos` lista los espacios de gastos compartidos y `/compartidos/[id]` es el detalle (balance, subcategorías, historial); `/objetivos-compartidos` y `/objetivos-compartidos/[id]` hacen lo mismo para objetivos compartidos; en rutas dinámicas el `usePathname()` de la navegación va dentro de `<Suspense>` (ver `Header.tsx`). Los layouts no se re-renderizan al navegar, por eso la auth se verifica en cada página, no en el layout.
- Para calcular "hoy" en el servidor hay que llamar `await io()` (de `next/cache`) antes; si no, `cacheComponents` falla por valor inestable.

### Datos (Firestore)
El navegador **no** accede a Firestore: `firestore.rules` bloquea todo y todo pasa por el servidor con firebase-admin.
- `users/{uid}/categories/{id}`: `{ type: "income"|"expense", name, description, icon, color, subcategories: [{id, name}], budget|null }`. Las subcategorías van embebidas en el doc. `icon`/`color` son claves de `lib/finance/catalog.ts`, mapeadas a componentes/clases en `components/categories/CategoryIcon.tsx`.
- `users/{uid}/transactions/{id}`: `{ type, amount, currency: "ARS"|"USD", arsRate|null, date: "YYYY-MM-DD", month: "YYYY-MM", categoryId|null, subcategoryId|null, note, recurring }`. Sin `currency` = pesos (no hay migración). Las fechas son strings (sin problemas de zona horaria); `month` se deriva de `date` y es lo que se consulta (igualdad + orden en memoria, sin índices compuestos).
- `users/{uid}/cards/{id}`: `{ name, closingDay, dueDay, color }` (tarjetas de crédito). Una compra con tarjeta (`createCardPurchase` en `lib/actions/cards.ts`) crea **un movimiento por cuota** en `transactions`, con `cardId`, `purchaseId` (compartido por todas las cuotas), `purchaseDate` e `installment: {n, total}`. Cada cuota se fecha en el vencimiento del resumen que la cobra (compra después del cierre → resumen siguiente; vencimiento ≤ cierre → mes siguiente). Las cuotas se editan/borran como compra completa (`updateCardPurchase`/`deleteCardPurchase`); `updateTransaction` las rechaza.
- Consumos con tarjeta: además de `note` (lo que trae el resumen, suele ser el comercio) tienen `alias` opcional (≤40, "Zapatillas running"), igual en todas las cuotas. **Resúmenes pagados**: `users/{uid}/cardPayments/{cardId_YYYY-MM}` `{cardId, month, paidAt}` (`setStatementPaid`, `getPaidStatements` devuelve claves `cardId:YYYY-MM` de `statementKey`). Una cuota solo cuenta como gasto (balance, desglose, presupuestos, Bingo) si su resumen está pagado: `countedTransactions` la filtra en `DashboardView`; las de tarjetas eliminadas cuentan siempre. En la home, "¿En qué se fue?" agrupa cada tarjeta en una fila (`summarizeMonth(..., { groupCards })`, clave `card:<id>`, un renglón por consumo con su alias o la categoría) y la lista de movimientos muestra una fila por resumen (`StatementRow`, "Sin pagar" si no se pagó, sin sumar al neto del día) que lleva al detalle.
- Lógica pura de tarjetas (cronograma de cuotas, próximo vencimiento, `upcomingDues`) en `lib/finance/cards.ts`. `/tarjetas` muestra próximos resúmenes y compras en cuotas; los vencimientos de los próximos 7 días los comunica Bingo en la home (`BingoAssistant`).
- Importar resumen (`/tarjetas` > Importar resumen, `components/cards/StatementImport.tsx`): `analyzeStatement` (`lib/actions/card-import.ts`) manda el PDF/imagen (≤4 MB; `serverActions.bodySizeLimit` en `next.config.ts`, `maxDuration` en la página) a Claude Haiku (`lib/ai/statement.ts`, salida estructurada con zod, requiere `ANTHROPIC_API_KEY`) junto con las categorías de gasto para que sugiera una; no guarda nada. La vista previa es editable (moneda y monto de la cuota, n de total, categoría, mes del resumen = mes del vencimiento) y arranca sin marcar lo que parece repetido (mismo monto y moneda ya cargado en esa tarjeta y mes). Los consumos en USD se importan en dólares con `arsRate` al dólar tarjeta. `importStatement` crea, por consumo, la cuota n en ese mes y las siguientes (`remainingInstallments`); las cuotas anteriores no se cargan. Son compras normales (`purchaseId`) con `importedFrom: "statement"`. En el selector de tarjeta, "Nueva tarjeta" la crea con nombre, día de cierre y de vencimiento leídos del resumen (editables en la vista previa). **Cupo** (`lib/data/statement-quota.ts`): 2 resúmenes por mes calendario por cuenta (`users/{uid}/statementImports/{sha256 del archivo}` con `quotaMonth`, `fingerprint` y el resultado en `extracted`) y por titular entre todas las cuentas (`statementQuota/{huella}_{YYYY-MM}` con `count`), descontados en una transacción después de leer con IA. La huella es un HMAC (`STATEMENT_HASH_SECRET`, o `FIREBASE_PRIVATE_KEY` si no está) del DNI sacado del CUIL/DNI del resumen, o nombre + últimos 4 dígitos, o tarjeta + fechas; el dato del titular nunca se guarda. Subir de nuevo el mismo archivo reutiliza `extracted` sin contar ni llamar a la IA. "Eliminar información" borra `extracted` pero conserva el cupo usado. El parámetro booleano `unlimited_statement_imports` de Remote Config (servidor, default false, condicionado al email del admin) saltea el cupo (`Flags.unlimitedStatements`).
- `users/{uid}/goals/{id}`: `{ name, target, currency: "ARS"|"USD", targetDate|null, icon, color, saved }` (metas de ahorro; la moneda solo cambia con `saved` en 0). `users/{uid}/goalMovements/{id}`: `{ goalId, amount (+aporte / −retiro), currency (la de la meta), date, month, note }`. `saved` se actualiza en una transacción junto con cada movimiento (`lib/actions/goals.ts`); no se edita desde el formulario de la meta. Lo apartado en el mes se muestra en el balance como "Apartaste $X · Libre $Y" (no es un gasto). Lógica pura en `lib/finance/goals.ts` (avance, cuánto apartar por mes).
- Contactos (base de lo compartido): `users/{uid}` guarda un perfil público `{email, emailLower, name, photo}` (se crea en `createSession` y al abrir `/contactos`; se busca por email exacto, nunca hay listados). `contactRequests/{fromUid_toUid}`: `{fromUid, toUid, status: pending|accepted|rejected, from, to}` (copias de nombre/email/foto). `users/{uid}/contacts/{otherUid}` se crea en ambos lados al aceptar. `sendContactRequest` responde igual exista o no el email (no revela quién usa la app) y acepta sola si la otra persona ya había invitado. Lo compartido (gastos/objetivos) solo se podrá abrir con contactos aceptados.
- Gastos compartidos: `shared/{id}` `{ kind: "expenses", name, icon, color, currency: "ARS"|"USD" (se elige al crear y no cambia; todos los `amountCents` están en ella), createdBy, memberIds: [uid], members: {uid: {name,email,photo,status: pending|accepted|left}}, subcategories: [{id,name}] }` (subcategorías propias del espacio; `memberIds` incluye invitados pendientes, no a quienes se fueron). Subcolección `entries`: `{ type: "expense"|"settlement", paidBy, amountCents, date, month, subcategoryId, note, split: {uid: cents}, createdBy }`. **Montos en centavos enteros.** Un ajuste (`settlement`) cuenta como que `paidBy` pagó y al destinatario le corresponde, así el saldo vuelve a 0 sin ser un gasto. Saldo = pagó − le corresponde (`computeBalance`/`balanceBySubcategory` en `lib/finance/shared.ts`). Solo se invita a contactos aceptados; cada uno borra lo que cargó; quien creó el espacio lo elimina y quita personas. UI: solo números (línea de balance con un indicador que se corre hacia quien pagó menos, `BalanceLine`), sin leyendas de deuda.
- Objetivos compartidos: mismo `shared/{id}` con `kind: "goal"` y `goal: {targetCents, targetDate|null}`; las `subcategories` son los conceptos (alquiler, vuelos…). Las `entries` son `type: "deposit"|"withdrawal"` con `paidBy` (quien aportó), `amountCents` y `subcategoryId`, sin `split`. Reservado = aportes − retiros (`computeGoalProgress`/`progressByConcept`); no se puede retirar más de lo reservado ni borrar un aporte que deje el total en negativo. Invitaciones, miembros y ajustes se comparten con los gastos (`loadSpace`, `SpaceForm`, `SpaceSettingsButton`); `getSharedOverview(kind)` y `getSharedDetail(id, kind)` filtran por tipo.
- Al crear/editar un espacio (`SpaceForm`) se elige una **categoría** (las propias con subcategorías + las sugeridas de `suggestionCategories`) y de ella salen los conceptos/subcategorías sugeridos, que se activan y desactivan como chips; al crear, la categoría fija ícono y color. No se puede agregar otro renglón mientras haya uno vacío.
- Lo compartido en el resumen personal (opt-in por espacio): `users/{uid}/sharedLinks/{spaceId}` `{categoryId|null}` (se activa en los ajustes del espacio con `setSharedLink`). `getSharedMonthSummary(month)` (`lib/data/shared-links.ts`) devuelve, para el mes: **mi parte** (`split[uid]`) de cada gasto como `Transaction` de solo lectura con `sharedSpaceId` (id `shared:<space>:<entry>`, en la categoría elegida; no se edita ni se desliza, la fila lleva al espacio) y mis aportes/retiros de objetivos como `GoalMovement` (suman a "Apartaste"). `(app)/page.tsx` los mezcla con los propios; los ajustes de pago entre participantes no cuentan. Lo que adelanté por otro no es gasto mío.
- Avisos push (FCM, PWA): `public/sw.js` (sin SDK de Firebase) muestra la notificación a partir de un mensaje **solo `data`** `{title, body, url}` y abre `url` al tocarla; se excluye del `proxy.ts`. `PushToggle` (menú de usuario y menú lateral) pide permiso, registra el SW, obtiene el token con `NEXT_PUBLIC_FIREBASE_VAPID_KEY` y lo guarda con `savePushToken` en `users/{uid}/pushTokens/{hash}` (uno por dispositivo; el token también se recuerda en localStorage). `lib/data/push.ts`: `notify(uids, payload)` envía después de responder (`after`) con `sendEachForMulticast` y borra tokens vencidos. Se dispara al: recibir/aceptar solicitud de contacto, ser invitado o unirse a un espacio, y cuando otro carga un gasto, pago o aporte. En iPhone solo funciona con la app instalada en la pantalla de inicio. Los íconos del aviso son SVG (algunos Android muestran el genérico).
- Tiempo real: `liveSignals/{uid}` (solo lo escribe el servidor con `touch`/`notify` de `lib/data/live.ts` y `push.ts` cuando una acción afecta a OTRA persona). `components/live/LiveSync.tsx` (montado en `(app)/layout.tsx`) obtiene un token personalizado (`getRealtimeToken`), escucha ese único documento con `onSnapshot` y ante un cambio hace `router.refresh()` (debounce 400 ms; también al volver a primer plano). Las reglas de `firestore.rules` solo permiten leer el propio `liveSignals/{uid}`; los datos siguen leyéndose únicamente desde el servidor, por eso no se usa TanStack Query (la app es server-first con RSC y `cacheComponents`; un caché cliente duplicaría el de Next). Hay que desplegar las reglas: `firebase deploy --only firestore:rules`. Para que un cambio llegue en vivo a otra persona, llamar `touch([uids])` en la acción.
- Feature flags (Remote Config, servidor): `lib/flags.ts` (`getFlags`, plantilla de servidor con caché de 60 s por instancia; sin Remote Config todo queda apagado). Parámetro `enable_data_reset` (boolean, default false) en Firebase Console > Remote Config > pestaña Servidor; se evalúa con señales `uid`/`email`/`randomizationId` para poder apuntarlo a una persona. Gatea el módulo **Eliminar información** (`/eliminar-datos`, `deleteAllMyData` en `lib/actions/account.ts`): borra movimientos, categorías, tarjetas, metas, contactos y vínculos, y sale de los espacios compartidos (`exitSpace`); conserva la cuenta de Google y el perfil. El flag se vuelve a comprobar en la acción y en la página; el enlace del menú sale con `FlagGate` en `Header.tsx`. Requiere la API de Remote Config habilitada en el proyecto.
- Mi negocio (antes Emprendimiento, `/negocio`): `users/{uid}/orders/{id}` `{clientId, client, phone, detail, amount, priority, deliveryDate, status: taken|in_progress|delivered|cancelled, materials: [{materialId,name,qty,unitPrice}], paid, remindedFor}`, `orderPayments` `{orderId, client, amount, date, month, note, transactionId|null}`, `materials` `{name, unit, unitPrice, stock, minStock}`, `materialPurchases` `{materialId, name, qty, total, date, month, supplier}`, `clients` `{name, phone, note}`, `businessExpenses` `{concept: shipping|packaging|tools|marketing|services|other, amount, date, month, supplier, note}` y `settings/business` `{targetMargin}`. `paid` y `stock` cambian en transacciones (`lib/actions/business.ts`). El stock baja al pasar a Entregado y vuelve si sale de ese estado; una compra suma stock, fija el precio y es gasto. **Clientes**: el pedido guarda `clientId` y una copia del nombre/teléfono; al guardar sin `clientId` se busca por nombre normalizado (`normalizeName`) o se crea el cliente; los pedidos viejos se enlazan solos la primera vez que se abre la página (`linkOrphanOrders`); editar un cliente actualiza la copia en sus pedidos y solo se borra un cliente sin pedidos. **Balance**: de caja (cobros − compras − gastos), con el mismo `BalanceViewSwitcher`/`MonthSwitcher`/`PeriodPicker` de la home vía `basePath="/negocio"` (ahí no se guarda la cookie). `businessMetrics(data, range)` da ganancia, margen, gastos por concepto, entregados, ticket promedio, margen por pedido (precio − materiales), por cobrar y mejores clientes; `suggestedPrice` propone el precio según el margen objetivo. Pestañas Resumen/Pedidos/Clientes/Stock/Gastos (`?t=`). Proveedor: texto libre en compras y gastos (base para analizarlos más adelante). **Impacto en la home (siempre)**: `getBusinessHomeTransactions(range)` arma con `businessHomeTransactions` movimientos de solo lectura (`business: true`, id `business:…`, categoría sintética `businessCategory` con clave `business`, subcategorías = conceptos) que `(app)/page.tsx` mezcla con los propios; suman al balance, salen en "¿En qué se fue?" como fila "Mi negocio", se filtran con `?c=business` y la fila lleva a `/negocio` sin deslizar. Los pagos viejos con `transactionId` (la casilla "sumar a mi resumen", que ya no existe) no se repiten: ya son un ingreso normal. Bingo avisa de entregas a 7 días y de stock bajo (`minStock`); el push de entregas lo manda `api/cron/deliveries` (cron diario en `vercel.json`, requiere `CRON_SECRET`, excluido del `proxy.ts`). Lógica pura en `lib/finance/business.ts`.
- Dólares: cada movimiento tiene `currency` (`ARS`/`USD`); los dólares se guardan en dólares y nunca se convierten. Al guardar uno en USD se guarda `arsRate` (pesos por dólar): `lib/data/fx.ts` la pide a dolarapi.com (`/v1/dolares/{casa}`, hoy, `use cache` + `cacheLife("hours")`) o a api.argentinadatos.com (`/v1/cotizaciones/dolares/{casa}/YYYY/MM/DD`, fechas pasadas), sin clave; si falla, `arsRate` queda null y la home lo completa con la de hoy (`fillRates`). Dólar de referencia en `lib/config.ts`: `USD_REFERENCE` (oficial) para movimientos y `USD_CARD_REFERENCE` (tarjeta) para compras con tarjeta e importados. `summarizeMonth` devuelve `income/expense/balance` y el desglose en pesos con los dólares por su equivalente (`toArs`), y además `ars` y `usd` por separado (`usd` null si no hubo dólares): `BalanceCard` muestra los pesos como balance principal y, si hay dólares, el bloque "En dólares" + "Todo en pesos ≈". Presupuestos, Bingo y la proyección usan el equivalente. Tarjetas: `statementTotal` devuelve `{ars, usd}` (`formatTotals` → "$ X + US$ Y"). Lógica pura en `lib/finance/currency.ts`; `formatMoney(value, currency?)`. Dólar de referencia por persona: `users/{uid}.usdReference` (oficial, bolsa = MEP o blue; `USD_REFERENCE_OPTIONS`), lo lee `getUsdReference()` y se cambia con `UsdReferencePicker` en el bloque "En dólares" de la home (`setUsdReference`); afecta el equivalente mostrado y la cotización que se guarda en los próximos movimientos (las tarjetas siguen al dólar tarjeta). Metas: cada meta tiene moneda; `netSaved` y `goalTotals` devuelven `{ars, usd}` y la home muestra "Apartaste" por moneda (el de dólares dentro del bloque "En dólares"). Espacios compartidos: `space.currency`; `money(cents, currency)` en `shared-ui.ts`, y mi parte/aportes llegan a la home en esa moneda. Mi negocio sigue solo en pesos.
- Lecturas: `lib/data/*` (DAL, `server-only`, cada función llama `verifySession()`). Escrituras: Server Actions en `lib/actions/*` (validan con zod, verifican que la categoría sea del usuario y del mismo tipo, y llaman `refresh()` de `next/cache`). Devuelven `ActionResult` en vez de lanzar.
- Al borrar una categoría, sus movimientos quedan como "Sin categoría". Las categorías sugeridas están en `lib/finance/defaults.ts` y se importan con `addDefaultCategories()` (no duplica por nombre+tipo).
- Lógica pura (formato de montos/fechas, `parseAmount`, `summarizeMonth`) en `lib/finance/`, usable en servidor y cliente.

### UI
- Server Components por defecto; `"use client"` solo para interacción (formularios, sheets, nav activa, menú de usuario).
- `components/common/ResponsiveSheet.tsx`: bottom sheet (vaul) en mobile, Dialog en desktop. Úsalo para formularios.
- La vista del mes es `components/dashboard/DashboardView.tsx` (solo presentación; `(app)/page.tsx` trae los datos). Recibe también el mes anterior para comparar y detectar fijos pendientes.
- `TransactionSheetProvider` aporta el formulario de alta/edición. Lo abren `QuickAddButton` (+ en el total de ingresos y − en el de gastos de `BalanceCard`), `ScrollAddButton` (+ flotante que aparece cuando esos totales salen de pantalla), `RecurringSuggestions` y las filas (`TransactionRow`, que además se deslizan para eliminar).
- Formulario: categorías ordenadas por uso, "Registrar de nuevo" (prefill) y la marca `recurring` (gasto fijo mensual).
- Desglose (`Breakdown`): dona SVG, comparación con el mes anterior y link a la lista filtrada por categoría (`?c=<categoryId|none>`). `BudgetsCard` usa `category.budget` (tope mensual, solo gastos).
- `TransactionList` es client: búsqueda local, filtro por `?c=` y días cargados de a 7.
- Evitar pantallas cargadas: listas largas usan `CollapsibleList` ("Ver N más"; no colapsa si oculta uno solo), el formulario muestra las 7 categorías más usadas + "Más" y las tarjetas de categoría muestran 4 subcategorías + "+N". Ojo: a un componente client desde un Server Component solo se le pasan props serializables (nada de funciones).
- Tema claro/oscuro con next-themes (`ThemeProvider`, `ThemeToggle` en el menú). PWA: `app/manifest.ts` + `public/icon.svg`.
- Navegación (`components/layout/AppNav.tsx`): en mobile, menú lateral (`SideMenu`, Drawer de vaul con `direction="left"`) abierto desde el botón ☰ del header, con el usuario y cerrar sesión al pie (llega del servidor como prop `footer`). En desktop, links en el header (`DesktopNav`). Las secciones se definen una sola vez en `ITEMS`.
- Asistente Bingo (home, solo mes en curso): `lib/finance/bingo.ts` (`bingoMessages`, lógica pura) decide qué casos aplican y arma textos amistosos con variantes estables por día; casos por prioridad: vencimientos (urgentes ≤2 días en alerta), sin categorías, gastaste más de lo que ingresó / sin ingresos, presupuesto superado o cerca, proyección de fin de mes, gasto mayor al mes pasado, fijos pendientes, meta cerca, hoy sin movimientos, te sobra plata y un mensaje base siempre presente. `components/brand/BingoAssistant.tsx` muestra uno a la vez (cerrable por sesión con `sessionStorage`, con 1/N para pasar al siguiente); el perro va sin padding en el borde con `overflow-hidden` y solo el texto lleva padding. Para agregar un caso, sumarlo en `bingoMessages` con su `priority`.

## Marca (Bingo)
- Paleta en `src/app/globals.css`: blanco cálido (`--background`), marrón rojizo como `--primary` (#9c3b22) y naranja como `--brand-orange` (#f28c28, clase `bg-brand-orange`/`text-brand-orange`). En oscuro el primario pasa a ser el naranja. Verde/rojo quedan solo para ingreso/gasto.
- Ilustraciones en `components/brand/Bingo.tsx` (SVG inline, sin el pan): `BingoDog` (`variant="hello"` en el login, `"wallet"` con la billetera en la home vía `BingoGreeting`), `BingoMark` (cabeza: header, menú, ícono) y `BingoWordmark` (logotipo).
- Tipografía del logotipo: Fredoka (Google Fonts, `font-brand`), letras con rebote y borde marrón. La fuente de Bluey es propietaria; Fredoka es la alternativa libre más parecida.
- Exportes estáticos en `public/brand/*.svg` e ícono PWA en `public/icon.svg`; se regeneran desde los componentes con `npm run brand:export`.
